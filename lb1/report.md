1. Авторизацію в системі.
2. Перехід до сторінки Products.
3. Додавання товару до кошика.
4. Перехід до кошика.
5. Оформлення замовлення.
6. Завершення замовлення.

Основний сценарій було виконано для перевірки коректної роботи основних функцій вебзастосунку.

## Контрольні питання
1. Що розуміють під якістю програмного продукту?
Це ступінь відповідності програми вимогам та очікуванням користувача.
2. Чому факт працездатності програми ще не означає її високої якості?
Програма може працювати, але мати помилки, незручний інтерфейс, низьку продуктивність.
3. Що таке аномалія?
Це відхилення фактичної поведінки програми від очікуваної.
4. Чому аномалія не завжди є дефектом? 
Тому що вона може бути запланованою або відповідати вимогам.
5. Що таке Expected Result та Actual Result?
Що мало відбутися, що відбулося фактично.
6. Які три питання використовуються для формування Title, Expected 
Що? Де? Коли?
7. Для чого потрібен defect report? 
Щоб чітко описати виявлену проблему та допомогти її відтворити й виправити.
8. Яку інформацію повинен містити defect report? 
Опис проблеми, середовище, кроки відтворення, Expected Result, Actual Result, докази, Severity та Priority.
9. Для чого використовуються GitHub Issues? 
Для створення, документування та відстеження проблем.
10. Навіщо до Issue додавати screenshot або відеозапис? 
Щоб наочно підтвердити проблему та полегшити її відтворення.
11. Чим Severity відрізняється від Priority? 
Severity - наскільки проблема серйозна. Priority - наскільки терміново її потрібно виправити.
12. Для чого у defect report вказують test environment? 
Щоб знати, в яких умовах виникла проблема і мати змогу її відтворити.
